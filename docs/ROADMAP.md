# 第一阶段之后的规划与选项

调研日期：2026-09-19。状态：供选择的规划，尚未开始第二阶段实现。

建议选择 A（检索与评估实验），完成共同基础后，再按需要接 B（知识库应用）或 C（图谱与复杂问答）。工作量是单人有效开发时间的估算，不是交付承诺；模型下载、硬件适配、资料整理和学习耗时另计。

## 1. 当前起点：已核验的第一阶段

- Python >=3.11，无第三方运行依赖；TXT/Markdown → 字符分块 → 本地哈希向量 → JSON 索引 → 检索 → 抽取式回答/可选远程模型 → 引用校验 → 固定题集评估。
- 当前索引：3 份文档、5 个片段，分块 300 字符、重叠 50 字符、512 维哈希向量。
- 本次运行 `python3 -m unittest discover -s tests -v`：6/6 通过。
- 本次运行 `python3 run.py evaluate --output /tmp/rag-planning-evaluation.json`：30/30 通过，文件级证据命中率与无答案拒答率均为 1.0。原有 experiments/baseline.json 未覆盖。
- 题集：17 道直接事实、5 道多要点、1 道拒答行为知识题、1 道精确词、6 道无答案题。多要点不等于已经验证了跨文档多跳推理。
- 以上只验证本地路径；本次没有调用付费模型，也没有验证远程模型可用性。

### 为什么第二阶段先做评估与检索

当前默认 top_k=4，而索引总共只有 5 个片段。evaluation.py 的 evidence_hit 使用文件路径的任意命中，没有验证目标证据段落和多证据覆盖；引用校验确认片段属于上下文，不等于确认答案受到证据支持。因此 30/30 说明教学样例可跑通，不能据此认定真实知识库问答已经达到 100% 准确率。

现有结构也有三个升级约束：pipeline.py 硬编码 LocalHashingEmbedding；retrieval.py 用词面重合控制向量得分；ExtractiveGenerator 内部仍用同一 embedder 对句子打分。升级语义模型时需要一起处理这些连接点，不能只替换 embeddings.py。

## 2. 三条可选路线

| 选项 | 最适合的目标 | 阶段顺序 | 预计投入 | 成本与主要取舍 |
| --- | --- | --- | --- | --- |
| **A：检索与评估实验（推荐）** | 学懂 RAG、形成能解释的实验结果、技术作品 | P2 评估 → P3 检索 → P4 生成 → P5 实验交付 | 15–22 人日 | 可先本地 CPU 起步；语义模型和重排序需要下载及资源测试；界面后置 |
| **B：个人知识库应用** | 尽快导入真实 PDF、通过界面问答 | P2 评估 → P3 精简语义检索 → B4 文档接入 → B5 应用交付 | 18–28 人日 | 更重视解析、引用和文档生命周期；扫描 PDF/OCR 增加适配成本 |
| **C：图谱与复杂问答实验** | 跨文档实体关系、多跳或全局问题研究 | P2 评估 → P3 混合检索基线 → C4 查询分解 → C5 图谱对照 | 22–35 人日 | 标注、实体抽取、建图与模型调用成本更高；收益取决于实际题型 |

这些是不同优先级，不要求永久三选一。A 的评估和检索成果可被 B、C 复用。若每周投入 10 小时，A 按每人日 6 小时粗算约 9–14 周。

## 4. 推荐路线 A：后续阶段与验收

### P2：建立可信评估基线（3–4 人日，所有路线共用）

目标：能够回答“改动究竟提升了哪类问题”。

1. 保留现有 30 题作为回归集。新增 60–100 题，基于至少 20 份有明确来源的中文资料；覆盖同义改写、编号/专有名词、跨段证据、跨文档证据、近似但无答案、版本冲突和噪声文档。
2. 开发集与封存测试集按来源/问题家族拆分，避免同题改写泄漏；只在开发集调参数。
3. 用文档版本 + 原文证据区间/证据文本标注相关性。分块变化后重新映射证据，避免把易变化的 chunk_id 当永久标准答案。
4. 记录 Recall@k、MRR、所有必需证据是否齐全、引用有效性、拒答准确率、可回答问题的误拒率、逐题失败类型。
5. 保存 run_id、代码版本或源码摘要、语料与题集 hash、模型/分词器版本、分块参数、检索参数、各阶段延迟和可获取的 token 用量。

交付：版本化语料清单、标注题集、统一实验报告和逐题对比表。

验收：现有 30 题不回退；新增题集 100% 有人工核对的答案/无答案标签；手工检查 10 个样例的指标计算；同一离线配置可重复得到相同排序与指标。新增题集初始结果允许不好，必须完整暴露失败。

### P3：语义、关键词与混合检索（6–8 人日）

按顺序形成四组实验：哈希基线 → 语义向量 → BM25 → BM25+语义向量的 RRF 排名融合；在混合检索上额外比较 reranker。

- 定义最小 Embedding/ Retriever/ Reranker 接口，保留原基线；依赖使用可选安装项。
- 先在本机测试一个中文语义模型的索引耗时、峰值内存和查询延迟；资源不足则选择更小模型或用户指定的远程服务。
- BM25 明确中文分词策略并记录版本；新语义检索不沿用“没有词面重合就清零”的规则，原规则只留在基线。
- 先保留 JSON + 暴力检索，形成可解释对照。只有实际规模和测量结果需要时再引入向量数据库。
- 融合使用排名而非直接相加不同量纲的分数；保留各路候选、原分数、融合名次、重排序分数供检查。
- 分开设置候选召回数量与最终上下文数量；重排序只能改善已召回候选的排序，漏召回需要先修检索。
- 分块实验另起一轮：字符窗口对比段落/标题分块，其他参数固定。

交付：四组检索结果、重排序消融报告、模型资源记录，以及每种方法的失败案例。

建议验收门槛（待 P2 基线测得后锁定）：扩展测试集 Recall@5 相对哈希基线提升至少 10 个百分点，或基线已高于 0.85 时达到 0.95；MRR 不下降，精确词子集不回退。重排序若不能改善排名或不符合延迟预算，就保持关闭。报告必须同时给出样本量、逐题变化和延迟，不能只展示一个汇总分数。

### P4：生成可信度与拒答（4–6 人日）

- 固定 P3 的检索配置，对比抽取式生成与一个用户可用的模型；统一证据上下文与引用格式。
- 将“检索置信度/拒答”从任意原始 score 中分离。BM25、余弦、RRF、reranker 的分数不能共用当前 0.08 阈值；在开发集分别标定或引入统一证据判定。
- 处理 ExtractiveGenerator 对哈希句子打分的耦合；为单因素实验固定生成策略，避免同时换检索模型和句子选择策略造成归因混乱。
- 校验引用属于实际上下文且能定位原文；人工检查答案断言是否被对应证据支持。可选接入 Ragas 做辅助评估，保留评审模型版本、提示词及人工抽检结果。
- 区分不足、引用错误与运行错误；覆盖超时、有限重试和失败报告，记录每次问答的追踪编号。

交付：回答/引用/拒答对照集、延迟与调用量报告、失败分类。

建议验收：引用位置有效率 100%；封存无答案集拒答准确率 >=90%；可回答集误拒率 <=10%；至少人工抽检 30 个生成答案，其中证据支持合格率 >=90%。这些是计划门槛，不是已获得的成绩。LLM 评分不替代人工核对。

### P5：可复现实验交付（2–4 人日）

- 配置文件表达完整实验；一个命令运行指定配置并输出独立结果目录。
- 汇总指标、逐题差异、失败样例和资源成本；报告能追溯到语料、模型和配置。
- 文档给出 Windows PowerShell 与 WSL 两套明确命令；依赖版本固定，基础离线路径继续可运行。
- 若将项目纳入 Git，建立离线测试与小题集回归 CI；模型下载和付费评估单独执行。当前目录未检测到 Git 仓库，CI 是未来工作。

验收：从干净环境按文档可重现本地基线和一个增强配置；模型相关结果在固定版本下有可解释的误差范围；每份报告能解释至少 5 个失败或回退案例及取舍。

## 5. 路线 B：知识库应用的后续阶段

先完成 P2 与精简 P3（语义检索及 BM25 对照，重排序可后置），再开展：

| 阶段 | 范围与交付 | 验收条件 |
| --- | --- | --- |
| B4 文档接入，4–6 人日 | Docling 解析适配器；先文本 PDF/表格，再 OCR；扩展来源结构为页码、标题、必要时版面区域；解析失败可见 | 至少 10 份代表性文档覆盖文本、表格、扫描件；各类人工核对阅读顺序及引用定位；解析失败不可伪装为空文档成功 |
| B5 应用与生命周期，7–11 人日 | 单用户本地上传、索引进度、问答、片段与引用查看；文件内容 hash 去重；新增、更新、删除与索引失效；服务层复用 pipeline | 从导入到问答可完成；更新后答案引用新版本；删除后新查询不再召回旧内容；失败任务可重试；已有评估能通过同一服务链路复跑 |

优先交付本地单用户版本。公开访问、多用户权限、部署运维另列里程碑；如果实际用途需要团队共享，应把这些需求加入 B5 之前的设计。沿用 P4 的引用和拒答检查。

## 6. 路线 C：复杂问答与图谱的后续阶段

先完成 P2/P3，建立强的普通检索基线，再开展：

| 阶段 | 范围与交付 | 验收条件 |
| --- | --- | --- |
| C4 复杂问题与查询分解，4–7 人日 | 建立至少 30 道跨文档关系/多跳问题；标注每条必需证据；加入有预算上限的查询分解与证据合并 | 每个答案可追踪全部必要证据；限制子查询次数；报告相对单次混合检索的质量、延迟和 token 增量 |
| C5 图谱对照，7–12 人日 | 独立 LightRAG 后端；实体/关系来源映射；比较普通混合检索、查询分解、图谱检索；验证更新删除 | 同语料、同测试题、尽可能相同生成模型与上下文预算；计入建图和查询成本；图谱收益在封存题集得到验证，且来源可核对 |

采用条件：多跳子集的人工证据支持合格率相对强基线提升至少 10 个百分点，并满足事先约定的成本预算。未达到条件则把图谱保留为实验，不设为默认路径。Agent 循环应在查询分解带来明确收益后再考虑。

## 8. 选择建议

- **选 A**：优先掌握原理、优化效果、做出有实验依据的作品。最符合当前“学习实验室”的结构，建议默认选择。
- **选 B**：主要需求是把个人 PDF/笔记真正用起来，界面与导入体验优先。
- **选 C**：已有明确的跨文档关系问题和相应数据，愿意投入建图与评估成本。
- **选 A→B**：先完成 P2/P3，再开发真实资料接入和界面，是学习与实用兼顾的推荐组合。

路线选择之后再确定资料领域、每周投入时间、CPU/GPU 条件以及是否允许远程模型调用。这些信息影响模型和排期，但不妨碍先完成共同的 P2。
